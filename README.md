# Hanjiang Sanguo (悍将三国) - Modern Edition

> A high-performance Three Kingdoms tactical card RPG game server reconstructed with modern **PHP 8.4+** and **Workerman 5.x**.

[English](README.md) | [简体中文](README.zh-CN.md)

---

## 📖 Overview

This project is a modern, high-concurrency re-architecture of the classic strategy RPG web/mobile game *Hanjiang Sanguo* (悍将三国). 

The original 2012~2015 server was built on legacy PHP 5.x + Apache + CodeIgniter with synchronous blocking MySQL queries and HTTP short-polling. While the game logic and tactical nine-grid combat mechanics were solid, its runtime architecture suffered from severe performance bottlenecks and required complex multi-instance partitioning (`s1`, `war`, `battle`, `report`, `uc`).

This modern edition rebuilds the backend into a resident-memory, event-driven microservice system that dramatically outperforms the original legacy stack while maintaining complete backwards compatibility with original client protocols.

---

## ⚡ Key Architectural Upgrades

| Feature | Legacy 2013 Edition (PHP 5.x + FPM) | Modern Edition (PHP 8.4+ & Workerman 5) |
| :--- | :--- | :--- |
| **Execution Model** | Stateless short process, reloads code on every request | **Resident in-memory processes**, zero bootstrap overhead |
| **Concurrency / IO** | Synchronous blocking MySQL and file IO | **Event-driven non-blocking IO** (Revolt / EventLoop) |
| **Combat Simulation** | Database-dependent sequential execution (~10-50ms) | **Pure in-memory deterministic simulation** (< 0.1ms) |
| **State Sync** | Client HTTP short-polling every second | Native **WebSocket duplex real-time broadcasting** |
| **Media Streaming** | Full-payload response (fails on Safari / iOS WebKit) | Standard **HTTP 206 Partial Content** Byte-Range slices & Capture-phase unlock |
| **Language Standards** | Dynamic typeless PHP 5.3, procedural helpers | **`declare(strict_types=1)`**, Enums, Readonly classes, Match |
| **Deployment** | Heavy Windows / WAMP / IIS dependencies | Single-command CLI / Docker containerization |

## 🚀 Quick Start

### Prerequisites

- **PHP >= 8.3** (PHP 8.4+ recommended)
- PHP extensions: `ext-pcntl`, `ext-posix`, `ext-json`, `ext-mbstring`, `ext-pdo_mysql`, `ext-redis`
- Composer

### Installation

1. Clone repository:
   ```bash
   git clone https://github.com/owner888/sanguohanjiang.git
   cd sanguohanjiang
   ```

2. Install dependencies:
   ```bash
   composer install
   ```

3. Create an empty database (tables are created by the migrations when the server starts):
   ```bash
   mysql -uroot -proot -e "CREATE DATABASE IF NOT EXISTS zc_sanguo DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
   ```
   **Database migrations** run automatically: every `php server.php start` / `restart` runs the pending `database/migrations/*.php` (OmniPHP `MigrationRunner`, filename order, recorded in the `migrations` table) in the master process before the workers fork, then closes that connection; a failed migration aborts the start. On an empty database the first migration (`0000_00_00_000000_import_base_schema`) imports `database/schema.sql`, which is always the complete current schema; on a database that already has the game tables it does nothing and is only recorded. By hand: `php tools/migrate.php status` (or `composer migrate:status`), `php tools/migrate.php` (`composer migrate`), `php tools/migrate.php rollback [batches]`; `reset` / `refresh` run every `down()` and require `--force`. The base migration's `down()` does nothing (rolling it back only removes its record, never the game tables). The tools use the same database settings as the server (`DB_DATABASE=other_db php tools/migrate.php status`).

   **Writing a migration**: `php tools/make-migration.php add_foo_to_member` (or `create_foo_table`) generates `database/migrations/YYYY_MM_DD_HHMMSS_<name>.php`. Migrations must be idempotent: check `Schema::hasTable()` / `hasColumn()` / `hasIndex()` before every step, because a fresh install already has the change from `schema.sql`. Write the same change into `database/schema.sql` in the same commit. Use full table names (`zc_sanguo_xxx`; the migration connection has no table prefix) and raw DDL in the `schema.sql` style. Never change a deployed database by hand.

5. Run test suite:
   ```bash
   composer test
   ```

   Developer recharge (no payment channel is wired yet): `php tools/pay_grant.php <uid> <productId>` credits product `productId` (`AlipayProduct`, run without arguments to list them) to player `uid` through the same payment core a channel callback will use (`Hanjiang\Model\Pay::complete`: gold, VIP progress, first-recharge state, mail, `pay_order` / `pay_log`) with an order id prefixed `manual_`. It is a CLI script only; no HTTP route reaches it.

   In-game test recharge: start the server with `PAY_TEST=1` (config `pay_test` in `config/app.php`) and the settings popup shows a "测试充值" button listing the products; each one calls `c=pay&m=test_grant&id=<productId>`, which credits the logged-in player through the same core as `pay_grant.php` (`Pay::grantManual`, channel `manual`). `c=pay&m=test_info` returns `{enabled, list}` so the client only shows the button when enabled. When `PAY_TEST` is not `1` (the default), `test_grant` returns status `0` and does nothing. **Never enable `PAY_TEST` in production** — it lets any player credit gold for free.

Unknown names are ignored with one log warning. `all` covers only activities whose module is ported: `sacrifice`, `exercise`, `flop`, `dailysign`, `rebate`, `blackmarket`, `jadegamble`, `beatengod`, `jump_rebate`, `sacredtree`, `compete`, `viprepay`, `pass_general`, `total_login`, `year_happy`, `login_reward`, `double_tower`, `double_heaven`, `double_mine`, `double_refine`, `double_talent`, `double_vip`, `double_beauty`, `double_miss`, `double_sanctum`, `double_hero`, `double_copies`, `gvg` (only the GVG bet / promotion reward crons read it; the GVG matches themselves run on fixed days of the month), and the Spring Festival series `act_newyear` (task counters only; the client has no blessing UI), `newyeardailysign`, `newyearpay`, `springlottery`, `springshop`, `newyearboss`, the second festival batch `christmasbuy`, `christmasgift`, `halloween`, `moon`, `national_day`, `acttanabata`, `national_celebration`, `anniversary`, `chingming`, and the third batch `acttreasure`, `worldcup`, `actkemari`, `sevenstar`, `actenrichment`, `paychecks`, `recall`, `actthirty`, `general_only`, `general_onsale`, `limitedshop`. The window is computed once per process and stays fixed, so the after-end settlement crons (Beatengod, Flop, Exercise, PassGeneral, Compete) just see "not ended" and never settle on each restart; if a process outlives the window they settle once, as in the legacy server. **Never enable `ACTIVITY_OPEN` in production** — it opens paid and reward activities for every player.

   **Configuration**: every setting in `config/*.php` reads an environment variable first; put local overrides in a `.env` file in the project root (`KEY=VALUE` per line, git-ignored, loaded by `bootstrap.php`; real environment variables win over `.env`). Common keys: `HTTP_LISTEN` (default `http://0.0.0.0:18100`), `HTTP_WORKERS` (4), `WS_LISTEN` (`websocket://0.0.0.0:18101`), `WS_PUBLIC_PORT`, `DB_HOST` / `DB_PORT` / `DB_DATABASE` / `DB_USERNAME` / `DB_PASSWORD`, `REDIS_HOST` / `REDIS_PORT` / `REDIS_PASSWORD` / `REDIS_DB`, `APP_TIMEZONE` (default `Asia/Shanghai`), `LOG_LEVEL` (`info`), `PAY_TEST`, `ACTIVITY_OPEN` / `ACTIVITY_OPEN_DAYS`, `SERVER_ID` (this server's id, default 1), `REPORT_URL` (share-page prefix for `c=report&m=save`). Changing `.env` or `routes.php` needs `restart`; `reload` does not re-read them.

   **Cross-server systems**: the legacy game ran a separate user center (uc) and battle server shared by all game servers. This project runs as ONE game server and hosts both in-process (`src/Cross`; tables prefixed `zc_sanguo_uc_` / `zc_sanguo_battle_` in the same database with legacy column names; rows partitioned by `serverid` = `SERVER_ID`; `zc_sanguo_uc_server` holds this server's row, whose `starttime` is the server open time). A real multi-server deployment needs all game servers to share the uc / battle tables (one shared database for them, or `src/Cross` extracted into a separate service), `zc_sanguo_uc_server` listing every server, and the code paths marked multi-server in `src/Cross` (other servers' teams, top 3, sacred trees and letters, martial tournament sync of other servers' entrants, GVG arena top 30 and team sync of other servers) implemented. The legacy martial tournament (`c=war`) server-side controller is not in the legacy package at all; `Cross\WarServer` is reconstructed from the s1 callers, the client and the battle tables (the inferred schedule and rules are listed in its class comment and in `docs/LEGACY_GAP.md`).

   **Runtime files and logs** (all under `runtime/`): `hanjiang.pid`; `logs/hanjiang.log` (Workerman master: start / stop / worker exits); `logs/hanjiang_stdout.log` (daemon mode stdout: per-request access log lines, PHP warnings / fatals, uncaught exceptions); `logs/{level}_YYYYMMDD.log` (OmniPHP Logger, e.g. `error_*.log` for unhandled HTTP exceptions, `warning_*.log` for protocol fallbacks; kept `LOG_KEEP_DAYS`, default 5).

   **Event loop**: workers run on Workerman's Fiber driver (Revolt, `revolt/event-loop`); every connection event and timer callback runs in its own Fiber. MySQL (PDO) and Redis (phpredis) calls are synchronous, so a request never suspends half-way and one process still serves one request at a time; request-scoped state lives in `Context` or in Fiber-local storage (`Workerman\Coroutine\Context`, used by `FlowLog`), never in static properties. Database migrations run in the master only on `start` / `restart`, before any fork, and that connection is closed before the workers start (see step 3).

## 🧪 Automated Testing

All core API endpoints and combat simulation loops are covered by PHPUnit integration tests (`tests/Feature`); legacy formulas in `LegacyStats` and team building in `TeamBuilder` are checked against real legacy database rows (`tests/Unit`):

```bash
./vendor/bin/phpunit                      # all suites
./vendor/bin/phpunit --testsuite Unit     # formulas and team building (TeamBuilder needs MySQL, no Redis)
./vendor/bin/phpunit tests/Feature/ItemStorageTest.php  # item storage models (spawns tests/Support/storage_worker.php processes for concurrency)
node tests/js/socket_io_adapter.test.js   # socket.io.min.js adapter (frame shape, heartbeat, address)
```

PHPUnit boots through `tests/bootstrap.php`: the same `bootstrap.php` and `routes.php` as the server, then one MySQL / Redis connection for the test process, so Feature tests run requests through the production middleware pipeline (`OmniPHP\Http\Router::dispatch`, via `tests/Support/Gateway.php`). `tests/Feature/HttpGatewayTest.php` drives `OmniPHP\Http\Kernel::handle` end to end: static files and their cache headers, the dynamic `config.js`, API entry points, CORS preflight, the `403` text response and the `-500` exception envelope. The test database must already have the full schema (`mysql --default-character-set=utf8mb4 -uroot -proot < database/schema.sql`, or start the server once on an empty database). `tests/Feature/MigrationTest.php` checks that the base migration is a no-op on that database and that a migration run on an empty scratch database (`zc_sanguo_migrun_test`, dropped afterwards) yields exactly the `schema.sql` tables (`SHOW CREATE TABLE`).

Elite real-time end-to-end smoke (starts the real server with the open-hours check pinned inside the window; test-only entry point):

```bash
php tests/e2e/elite_smoke_server.php start -d
node tests/e2e/elite_smoke.mjs            # two guests: create → join → startfight, both receive enterfight
php tests/e2e/elite_smoke_server.php stop
```
